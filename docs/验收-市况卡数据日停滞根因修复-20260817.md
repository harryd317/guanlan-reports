# 市况卡数据日停滞根因修复验收

验收日期：2026-08-17（Asia/Shanghai）

代码提交：`803c3b6362a75d6e1bb64bc0ecdc62d1b4248471`

结论：**PASS，已部署生产。**

## 1. 根因

页面停在 7 月 31 日不是市况引擎停跑，而是今天页把已退役 S2 缓存的日期和开仓门放在了真实市况投影之前。

修复前的取值链是：

1. `/api/regime/current` 读 `market.db.regime_history`，最新日期字段名为 `date`。
2. `/api/brief` 读 `screener.db` 中已退役 S2 的 `snapshots` / `daily_reports` 缓存。
3. `static/home.html` 使用 `briefPayload.date || pageState.regime?.trade_date`；旧缓存的 `2026-07-31` 永远先命中，同时页面还优先取 `briefPayload.market_gate` 并硬编码“中性市场状态”。
4. `/api/s3/summary` 另行读新鲜的 `breadth_daily`，造成同一张卡的日期、市况、开仓门和宽度可能不在同一 as-of 日。

引入该错误优先级的源变更至少可追溯到 `425d361`（2026-08-09 11:43）。影响时段记为该版本的生产部署窗口至本次修复部署（2026-08-17 23:16 左右）。影响仅在界面展示；市况引擎、策略、风控和各读取数据表在期间仍按原路径运行。

## 3. 调度审计

市况链由进程内 APScheduler 调用 `_market_daily_job`，顺序是行情增量、沪深300指数、`regime_history` 物化。它没有“每次运行一个操作系统进程退出码”；验收以 APScheduler 日志、内部错误日志和物化表写入时间三方对账。`_market_daily_job` 会捕获并记录内部异常，因此单看 APScheduler 的 `executed successfully` 不能证明三段均成功。

8 月的任务每个交易日均有调度或哨兵回补记录，但存在 DNS 失败、主机休眠/错过与延迟：

- 08-06、08-10、08-14 已由哨兵回补。
- 08-05 因 Tushare/Sina DNS 解析失败仍是历史缺口。本任务没有回填，因为那会写生产库，需要用户另行逐次授权。
- 08-05 缺口不是界面停在 07-31 的原因；后续 `regime_history` 和连阳名单都持续更新。

逐日证据见 [`scheduler-audit.md`](../reports/regime-freshness-20260817/scheduler-audit.md)。

## 4. 修复

1. 新增 `market_status.py` 只读投影：SQLite URI `mode=ro` + `PRAGMA query_only=ON`，不调用会初始化表的 `regime.current()`。
2. 在 `market_daily`、`index_daily`、`regime_history`、`breadth_daily` 中找四表共同存在的最近交易日，市况、开仓门、指数距离和宽度全部精确读该日。
3. 开仓门只重放已冻结的 `backtest_mid.gate_map`，截止于共同日；没有修改策略或参数。
4. 今天页市况卡仅使用 `/api/regime/current` 的同日投影，删除 S2 `brief` 日期/开仓门的界面降级路径，删除“中性市场状态”硬编码。
5. freshness 同时检查四个输入的 `MAX(date)` 和四表共同投影日。任一来源缺失或相对预期交易日落后超过 1 个交易日，卡片必须显示“数据停滞”。这也覆盖“四表各自 MAX 很新，但中间缺行使共同日回退”的边界。

本修复没有人工写生产数据库。按用户要求重启后，既有生产调度器自动执行了原有增量/快照任务和 SQLite checkpoint；这些不是本修复的手工写入。重启前后逻辑最新日和行数不变，文件级哈希变化及原因已如实记入 [`production-hashes.json`](../reports/regime-freshness-20260817/production-hashes.json)。
