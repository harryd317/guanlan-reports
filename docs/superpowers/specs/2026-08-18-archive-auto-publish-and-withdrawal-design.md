# Kimi 审校通过自动发布与档案撤回设计

**日期：** 2026-08-18  
**性质：** 档案生命周期收敛，不改 S8 策略口径、档案规格 v2 或审计表结构。

## 目标与不变量

当行业的 Kimi 审校意见已落库且结论为“通过”（包含“复尺通过”）、审校镜像提交哈希已通过 40/64 位格式校验、正式档案已提交且通过规格 v2 与现有档案门槛时，服务端自动调用现有 finalize 发布语义，队列转为 `resolved`。

以下不变量必须保持：

- “改后再审”、“重写”、“不通过”不触发发布，现有返修流程不变。
- 正式档案缺失或校验失败时，审校意见仍须持久化，队列保持待自动收敛。
- 自动发布审计的 `actor` 固定为 `auto-on-kimi-review`，`reason` 精确记录对应审校意见的镜像提交哈希；既有日志字段不变。
- 撤回后队列状态成为 `withdrawn`，保留 `archive_id` 作为历史证据，但 S8 只认 `resolved` 为已解锁，因而立即重新锁定。
- 日常队列刷新、季度复核和启动收敛不得把 `withdrawn` 覆盖或自动再发布。

## 方案选择

采用“领域服务收敛 + 启动幂等补偿”：

1. 审校写入与审计落库成功后，同一服务调用自动发布判定。
2. 自动发布复用现有 `publish_reviewed_archive` 的 v2 校验、正式档案匹配和队列事务，不建第二套发布口径。
3. 生产服务在数据库初始化后执行一次幂等收敛，处理“审校先落库、正式档案后随代码部署到达”的存量顺序。
4. 等效环境的只读模式不运行收敛，避免验收程序意外写入复制库。

未采用的方案：

- 不由前端在审校后再调 finalize，因为浏览器关闭或请求中断会使状态永久停留。
- 不用 SQLite 触发器直接发布，因为触发器无法审阅 Git 已提交的 Markdown 正文与规格 v2。
- 不以删除档案文件实现撤回，因为这会损失历史证据。

## 状态机

| 当前状态 | 条件/事件 | 下一状态 | 动作 |
|---|---|---|---|
| `awaiting_review` | Kimi 结论为改后再审/重写/不通过 | 保持现状 | 仅写审校与审计 |
| `awaiting_review` | 通过，但镜像哈希或正式档案条件不全 | 保持现状 | 显示等待自动发布的缺口 |
| `awaiting_review` | 通过 + 哈希已验证 + 正式档案 v2 通过 | `resolved` | 自动 finalize，写 `actor=auto-on-kimi-review` |
| `resolved` | 段睿或 Kimi 经镜像投递有效撤回指令 | `withdrawn` | 保留档案证据、写撤回审计、重锁 S8 |
| `withdrawn` | 常规刷新/启动收敛/季度复核 | `withdrawn` | 无动作，禁止静默复活 |

## 结论判定

判定只读取审校正文的结论行：去除“结论：”后，仅接受以“通过”或“复尺通过”开头的明确结论。任一否定词“不通过”、“未通过”、“改后再审”、“重写”优先阻断，避免子串误判。

## 撤回边界

新增服务端撤回入口，请求必须同时满足：

- `actor` 严格为“段睿”或“Kimi”。
- 撤回原因非空。
- 指令的镜像提交哈希为 40 或 64 位小写十六进制。
- 当前行业已发布且有 `archive_id`。

撤回审计保持原表字段：`action=withdraw`，`actor` 保留指令者，`reason` 记录人类原因及镜像提交哈希。队列 `human_note` 仅保留可向页面展示的撤回原因。

## 页面与读模型

- 待终审页删除“通过并发布 / 退回修改 / 改完直接发布”三个按钮。
- 原固定警示保留，新卡片展示“等待 Kimi 审校 / 等待正式档案 / 已自动发布 / 等待返修”等派生状态，并说明撤回必须由段睿或 Kimi 通过镜像投递指令。
- `withdrawn` 不再被读模型当作“已发布”。档案详情继续可读，但顶部显示“已撤回”、原因及“不构成有效 S8 档案依据”。
- 不增加页面撤回按钮；指令只能通过服务端受控入口到达。

## 存量收敛

本次随代码提交两份已复尺通过的正式档案：通用设备、饲料。正文与已审校返修稿逐字一致，仅增加正式档案 front matter。部署重启时幂等收敛两行已通过审校。

动物保健Ⅱ当前最新意见为“改后再审”且无已验证通过意见，保持原状态。其他没有同时满足三个条件的存量行全部保持。

## 验证与部署

验收包括：领域状态机单测、服务端入口契约、日常刷新/季度复核保护、读模型与前端文案、全量回归、规格 v2 重跑、生产等效环境、桌面 1440×900 和手机 390×844 零滚动及撤回页展示。生产部署前后记录数据库哈希与逻辑行差异，证明只发生授权的存量生命周期写入。
