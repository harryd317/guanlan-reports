# 数据验真层设计

日期：2026-07-21  
状态：待用户审阅

## 1. 目标

在不改变中线选股语义和冻结参数的前提下，为收盘筛选增加可追溯的数据验真层。系统必须回答四个问题：每只股票用了哪一天的数据、来自哪个源、股票池市值是哪一天的、该数据是否允许产生新信号。

验真层只判断输入数据是否可信，不判断股票未来涨跌。它不能把“数据正确”表述为“选股有效”。

## 2. 已确认的产品原则

- 收盘规则只使用已完成的日线，不使用盘中半根K线。
- 日期不一致的股票不能产生 `capture`、`entry_A` 或 `entry_B`。
- 停牌、数据缺失和上游延迟必须分开记录。
- 主源失败后的备源切换必须留痕，不能静默混用。
- 每日抽查少量股票的双源一致性；不做全市场双源抓取。
- 为每个可交易信号冻结输入，便于日后复核数据修订。
- 页面只显示一条数据健康状态，不增加新的复杂操作入口。

## 3. 方案比较

### 方案A：只补逐票日期守门

为每只股票检查最后一根K线日期，旧数据直接跳过。改动最小，但无法追踪数据源、股票池日期和复权修订，也发现不了主备源口径分叉。

### 方案B：逐票强校验、来源留痕、抽样双源对账

逐票记录元数据，屏蔽陈旧数据，区分停牌和缺数；每天确定性抽样做双源对照；保存信号输入。该方案覆盖当前已知风险，扫描耗时和存储增长可控。

### 方案C：全市场双源计算和全量原始数据归档

每天同时抓取两套全市场长窗数据，并永久保存全部输入。覆盖最强，但网络请求、失败面、运行时间和存储成本接近翻倍；两套复权口径的正常差异还会制造大量假告警。

采用**方案B**。方案A证据不足，方案C违背当前“简单、稳定、可解释”的产品方向。

## 4. 边界

### 4.1 本次包含

- 股票池来源和市值日期留痕。
- 每只扫描股票的行情来源、行情日期、复权口径、取数状态和输入摘要。
- 逐票新鲜度守门。
- 停牌、数据缺失和源降级分类。
- 每日双源确定性抽样和差异摘要。
- `capture`、`entry_A`、`entry_B` 输入冻结。
- 快照、简明首页和历史接口的数据健康字段。
- 离线测试与一次真实收盘验收。

### 4.2 本次不包含

- 修改500亿元市值门槛、250日新高、RS前15%或任何买卖参数。
- 判断选股策略是否有效；该结论属于下一阶段“选股器独立体检”。
- 让AI解释或修复数据。
- 全市场双源强一致。
- 将盘中免费源升级为交易指令数据源。
- 美股数据接入。

## 5. 架构

新增独立模块 `data_trust.py`。它只处理元数据、状态分类、抽样和对账，不计算交易信号。

现有 `data.py` 继续负责取数，但新增带元数据的接口。旧接口保留，避免打断体检页、AI上下文和离线脚本。策略插件通过新接口向 `eod.py` 返回 `DataFrame + FetchMeta`。`eod.py` 先验真，再把通过的 `DataFrame` 交给原规则引擎。

数据流如下：

```text
股票池取数
  → 记录股票池来源和市值日期
  → 逐票拉长窗日K并记录来源/行情日期
  → 数据验真层分类 fresh / suspended / stale / missing
  → 仅 fresh 股票进入RS样本和规则引擎
  → 双源抽样复核
  → 新信号总闸门
  → 快照、信号输入、首页状态落库
```

## 6. 数据契约

### 6.1 股票池元数据

股票池结果附带：

```json
{
  "source": "tushare_daily_basic",
  "market_cap_date": "2026-07-20",
  "fetched_at": "2026-07-21 16:31:12+08:00",
  "degraded": false
}
```

Tushare当日 `daily_basic` 为空并退回上一交易日时，必须把真实日期写入 `market_cap_date`。东财备源无法证明日期时写 `null`，并把整场新信号闸门关闭；持仓管理和旧快照仍可读取。

### 6.2 个股行情元数据

每只股票产生一份 `FetchMeta`：

```json
{
  "code": "600000",
  "source": "tushare_pro_bar",
  "bar_date": "2026-07-20",
  "expected_date": "2026-07-20",
  "adjustment": "qfq",
  "fetched_at": "2026-07-21 16:32:01+08:00",
  "status": "fresh",
  "reason": null,
  "bar_hash": "sha256:..."
}
```

`bar_hash` 对排序后的 `date/open/high/low/close/vol` 标准化内容计算。它用于发现同一信号输入是否被上游修订，不用于恢复原始数据。

标准化格式固定为UTF-8 CSV：日期使用 `YYYY-MM-DD`，数值保留8位小数，列序和行序固定，文件以换行结尾。同一输入在不同进程和不同机器上必须得到同一哈希。

### 6.3 状态定义

- `fresh`：最后一根日K等于应有最新交易日，允许进入RS样本和规则引擎。
- `suspended`：交易所或数据源明确标记停牌。禁止新信号；持仓显示“停牌，判定顺延”。
- `stale`：最后一根日K早于应有日期，且无法证明停牌。禁止新信号，计入异常比例。
- `missing`：空数据、列缺失或有效K线不足。禁止新信号，计入异常比例。
- `fallback` 不是独立状态；它是 `source` 属性。备源数据仍须通过日期校验。

停牌证据主源为Tushare `suspend_d` 当日清单，按交易日整场缓存一次。接口不可用时不以“当日无K线”推断停牌。系统拿不到停牌证明时必须归类 `stale`，不能猜成停牌。

## 7. 新鲜度和整场闸门

当前代码用全池最后日期的最大值判断新鲜度。新设计改为逐票判断。

- `fresh` 股票进入RS分位样本和规则引擎。
- `suspended` 股票不进入RS样本，不计入异常比例。
- `stale` 和 `missing` 股票不进入RS样本，计入异常比例。
- 异常比例为0：数据健康状态 `pass`。
- 异常比例大于0且不超过10%：状态 `degraded`；只允许新鲜股票产生信号，首页明确显示屏蔽数量。
- 异常比例超过10%：状态 `blocked`；本轮不生成新信号，不覆盖上一份成功快照。异常写入独立验真运行记录。
- 股票池日期早于应有日期或未知：状态 `blocked`。

普通持仓和阶梯留仓统一使用逐票日期校验。陈旧或停牌数据只发 `HOLD/REVIEW` 提醒，不得触发卖出。

## 8. 双源抽样对账

每天按 `SHA-256(trade_date + code)` 排序，从新鲜股票中抽取5%，最少10只、最多20只。固定算法保证同一天重跑抽到同一批股票。

主源使用Tushare，复核源使用东财。对账先按日期内连接，再比较：

- 最后交易日是否一致；
- 近120日涨幅差是否不超过0.5个百分点；
- 最新20日量比差是否不超过0.05；
- 当日是否突破250日新高的布尔结果是否一致。

绝对前复权价格不直接比较，因为两源可能使用不同复权锚。原始成交量也不直接比较，因为单位可能不同。

处理规则：

- 单只样本不一致：记录明细；若该票产生新信号，则屏蔽该信号。
- 可比较样本中不一致比例超过20%：关闭整场新信号闸门，保存独立验真运行记录但不推进候选池。
- 备源不可用或可比较样本少于5只：状态 `unavailable`，页面提示“双源抽查未完成”；主源逐票验真通过时不因此关闭整场信号。

双源抽查是异常探针，不把东财升级成与Tushare等权的裁判。

## 9. 信号输入冻结

新增 `data_quality_runs` 表，记录每次扫描的预期日期、验真状态、聚合计数、双源结果、错误类别和完成时间。它保存成功、降级和拦截三类运行；被拦截的运行不写入 `snapshots`，因此不会覆盖上一份可信结果。

新增 `signal_inputs` 表，只保存 `capture`、`entry_A` 和 `entry_B`：

- `trade_date`、`code`、`state`、`rule_version`、`code_fingerprint`；
- 股票池来源和市值日期；
- 行情来源、行情日期、复权口径和 `bar_hash`；
- 规则实际读取的长窗日K，使用gzip压缩JSON；
- RS分位、基本面闸门输入和当次参数快照。

主键为 `(trade_date, code, state)`。同日补跑使用 `INSERT OR REPLACE`，不产生重复记录。信号输入保留一年；清理时保留元数据和哈希，只删除压缩K线正文。

这张表冻结“系统当时看见了什么”，不冻结未来行情。

## 10. 快照和页面

快照新增 `data_quality`，旧快照和旧前端不受影响：

```json
{
  "status": "pass",
  "expected_date": "2026-07-20",
  "universe_source": "tushare_daily_basic",
  "market_cap_date": "2026-07-20",
  "fresh_n": 376,
  "suspended_n": 0,
  "blocked_n": 0,
  "fallback_n": 0,
  "cross_check": {"status": "pass", "sample_n": 18, "mismatch_n": 0},
  "per_stock": {"600000": {"source": "tushare_pro_bar", "bar_date": "2026-07-20", "status": "fresh"}}
}
```

首页只增加一行：

- 绿色：`数据验真通过｜7月20日收盘｜376/376新鲜｜双源抽查18/18一致`
- 黄色：`数据降级｜3只已屏蔽，不会产生信号｜查看明细`
- 红色：`数据异常｜今日新信号已关闭｜继续显示上一份可信结果`

候选卡不增加常驻字段。详情页可展开查看该票的数据日期、来源、市值日期和输入哈希。

## 11. 故障和降级

- 主源单票失败后允许调用备源；元数据必须写实际来源。
- 备源也失败时归类 `missing`，不构造空K线或沿用旧值。
- 停牌状态接口失败时，陈旧票归类 `stale`。
- 数据验真模块自身异常时，默认关闭新信号；持仓页显示“数据验真未执行”，不得假装HOLD或发卖出。
- 数据质量异常写入 `data_quality_runs`，但不能推进候选池、AI研究或自动入池。
- 任何数据问题都不能删除上一份可信快照。

## 12. 测试设计

测试必须先失败，再实现。

### 12.1 单元测试

- 当日K线为 `fresh`。
- 昨日K线且有停牌证据为 `suspended`。
- 昨日K线且无停牌证据为 `stale`。
- 空数据为 `missing`。
- `bar_hash` 对相同数据稳定，对任一OHLCV变化敏感。
- 抽样同日可重复，不同日期可轮换，数量符合5%/10/20边界。
- 双源比较忽略绝对前复权锚差，但识别收益、量比和突破状态差异。

### 12.2 编排测试

- 一只陈旧票和多只新鲜票并存时，陈旧票不进入RS样本且不产生信号。
- 停牌票不计入异常比例。
- 异常比例10%贴边允许落降级快照；超过10%保留旧快照。
- 股票池日期旧或未知时关闭新信号。
- 抽样不一致的信号票被屏蔽。
- 系统性双源不一致时不推进候选池和AI研究。
- 普通持仓和阶梯留仓在陈旧数据下都不触发卖出。
- `signal_inputs` 保存后可解压，参数和哈希与快照一致。
- 旧快照缺少 `data_quality` 时API和页面正常显示。

### 12.3 真实验收

一个真实交易日16:30后完成扫描，并满足：

1. 股票池日期、指数日期和所有非停牌股票的行情日期一致；
2. 页面显示数据健康状态和双源抽查结果；
3. 任何被屏蔽股票不出现在新信号组；
4. 当日每条新信号都有可解压的输入档案；
5. 第二次补跑结果幂等，不新增重复档案；
6. 原中线规则测试、Web测试和回测金丝雀全部通过。

## 13. 成功标准

完成后，系统可以证明“这份名单由哪一天、哪一来源、哪一版复权数据计算”，并在证据不足时停止发出新信号。它仍不能证明名单未来会上涨；下一阶段用独立前瞻收益体检回答这个问题。
