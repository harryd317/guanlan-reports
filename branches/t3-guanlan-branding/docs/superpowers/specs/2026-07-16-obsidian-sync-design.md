## 1. 背景

现有知识库只在 Claude 或 Hermes 主动写入 vault 后提交并推送。它不监控 screener，也不读取项目的新提交。Claude 没写 vault 时，定时任务只能确认“知识库没有变化”，无法发现项目已经前进。

Obsidian 的最后一份 screener 事实快照停在 2026-07-12 的 P0，测试基线为 `8/20/428`。项目随后从提交 `c4d4338`（P1 策略插件层）推进到 `d621afb`（池外查询连续对话），中间有 71 次提交、92 个变更文件和多项已上线或已证伪的结论。固定回填终点的测试基线为 `8/20/693/9`；终点之后的任务 21 提交 `ea3354d` 把当前基线推进到 `8/20/698/9`，由增量同步处理。

本设计先补齐这段历史，再建立不依赖任何 AI “记得写库”的自动同步链路。

## 2. 目标

系统必须做到：

1. 每个已提交的 screener 变更都进入 Obsidian 的覆盖记录。
2. 关键交付、研究证据、失败实验、用户决策、冻结纪律和事故教训可独立阅读。
3. 自动化失败时保留现场并重试，不静默跳过。
4. 原始事实与 AI 摘要分层保存。AI 摘要失败或写错时，原始证据仍完整。
5. 旧结论保留演变轨迹，并明确标记“已完成”“已替代”或“已证伪”。
6. GitHub 远端收到同步结果后，系统才确认该批次完成。

## 3. 非目标

本期不做以下工作：

- 不复制源代码、数据库、日志、交易截图或私人交易明细。
- 不读取或写入 `.env`、`.token`、API key、SendKey 等凭证。
- 不把未提交文件当成已完成事实；未提交改动只产生提醒。
- 不改变 screener 的交易规则、服务、定时扫描或生产数据。
- 不让 AI 直接改写历史证据文件。

## 4. “全部信息”的口径

“全部信息”分为三层。三层共同保证完整性和可读性。

### 4.1 原始证据层

自动镜像已提交的 Markdown 文档到：

`10-项目/screener/源材料/`

纳入范围采用确定性白名单：

- `CLAUDE.md` 与 `MEMORY.md`；
- 提交中新增、修改、重命名或删除的全部 `docs/**/*.md`；
- 以后明确加入配置白名单的其他项目级 Markdown。

计划、设计、交付总结、实验记录、研究报告、失败收档和评审材料都在镜像范围内。同步器不让 AI 判断一篇 Markdown 是否“重要”。

HTML 原型只进入索引，保留文件名、提交号和用途，不复制到 vault。代码改动只进入提交流水，不复制正文。

`源材料/` 是脚本管理的只读镜像。人和 AI 不在其中手工编辑。

### 4.2 覆盖审计层

`10-项目/screener/变更流水.md` 为确定性账本。每个提交占一行，至少包含：

| 字段 | 含义 |
|---|---|
| commit | 完整或可唯一定位的提交号 |
| 时间 | Asia/Shanghai 提交时间 |
| 标题 | 原始提交标题 |
| 变更类型 | 交付、研究、修复、文档或运维 |
| 证据文件 | 本次提交对应的源材料 |
| 主题笔记 | 内容沉淀到哪篇可读笔记 |
| 状态 | 已镜像、已摘要、待摘要或失败 |

这张表必须覆盖回填区间的全部 71 次提交。以后每次同步继续追加，禁止删除历史行。

### 4.3 可读知识层

自动化根据已镜像证据生成带来源引用的日期摘要。摘要只写追加型文件，不直接重写历史笔记。一次性回填时，人工校正现有长期笔记。

## 6. 自动同步架构

### 6.1 触发方式

系统采用双触发：

1. screener 提交完成后，`post-commit` hook 异步启动同步器；
2. launchd 每 15 分钟补跑，覆盖 hook 缺失、Mac 睡眠和临时网络故障。

hook 只负责唤醒，不承担同步逻辑。同步器失败不得影响 screener 的提交。

### 6.2 同步器

运行入口使用英文路径：

`~/.local/bin/screener-vault-sync`

项目内保留可版本化的源脚本和测试。安装步骤把入口复制到英文路径，避免 launchd 在中文路径下出现权限或解析问题。

同步器依次执行：

1. 获取本地互斥锁，防止 hook 与 launchd 并发写库。
2. 读取两个游标：原始镜像游标与摘要游标。
3. 检查 screener 和 vault 路径、Git 分支与远端状态。
4. 按提交区间收集日志、文件列表和允许镜像的 Markdown。
5. 幂等更新源材料镜像与变更流水。
6. 调用修正后的 vault 自动同步，提交并推送原始证据。
7. 验证 `main` 与 `origin/main` 无领先或落后；一致后推进镜像游标。
8. 调用本机 Hermes API，生成来源受限的结构化摘要。
9. 校验摘要格式、来源提交和敏感信息。
10. 写入日期摘要或待整理材料，再次提交并推送。
11. 远端一致后推进摘要游标。

### 6.3 双游标

状态文件放在 `~/.local/state/`，不进入知识库：

- `screener-vault-mirror.head`：原始证据已经镜像并推送到的最后提交；
- `screener-vault-digest.head`：可读摘要已经生成并推送到的最后提交。

Hermes 不可用时，原始镜像仍可完成并推进镜像游标；摘要游标停在旧位置。下次任务只补摘要，不重复制造流水行。两个阶段分别提交，AI 故障不能阻止原始证据进入远端。

## 7. AI 摘要约束

Hermes 只处理同步器提供的提交日志和镜像文档。提示词禁止补充外部事实，输出必须包含以下栏目：

- 本批交付；
- 研究结论与数字；
- 被证伪或终止的方案；
- 用户拍板与冻结边界；
- 新待办和已过期待办；
- 事故与方法论；
- 来源提交和来源文件。

每条事实至少引用一个提交号或源材料文件。无法找到来源的内容不得进入正式摘要。

AI 输出只写日期摘要和 `最新状态-自动生成.md`。主题历史、源材料和变更流水由确定性逻辑保护。现有 Hermes 定时复核继续检查事实冲突和敏感信息。

## 8. 未提交工作

同步器只认 Git 提交。发现以下情况时，它写日志并发出提醒：

- `docs/`、`CLAUDE.md`、`MEMORY.md` 或 `AGENTS.md` 有未提交变更；
- 新增交付总结、实验记录或研究材料尚未提交；
- 源代码已经提交，但对应交付或实验文档缺失。

提醒不能把工作区内容复制进 vault。当前未提交的 `AGENTS.md` 适用这条规则；任务 21 原型已经随 `ea3354d` 提交，不再属于未提交缺口。

## 9. 并发、失败与恢复

同步器用原子写入和互斥锁保护 vault。任何步骤失败都记录到：

`~/Library/Logs/screener-vault-sync.log`

错误信息必须包含时间、失败阶段、提交区间和是否推进游标。日志禁止包含文档全文和凭证。

恢复规则：

- Git 拉取失败：停止写入，不推进游标；
- 镜像失败：停止本批，不推进镜像游标；
- Hermes 失败：保留原始镜像，摘要游标不动；
- Git 提交失败：保留工作区，不推进游标；
- Git 推送失败：保留本地提交，不推进游标；
- 重跑同一区间：结果必须幂等，不增加重复流水或重复摘要。

现有 `vault-autosync.sh` 曾出现 `fatal: Cannot rebase onto multiple branches` 和 SSH 连接失败。实施时必须先修复退出码检查与单分支拉取，再把它接入新链路。

## 10. 安全边界

同步器使用路径与文件类型白名单。以下内容永远排除：

- `.env`、`.token`、SSH key 和任何凭证文件；
- `*.db`、`*.db-*`、`positions.csv` 和交易截图；
- `web.log`、系统日志和临时目录；
- `static/`、Python 源码和测试夹具正文；
- Markdown 中疑似密钥、Authorization header 或长串 token。

敏感信息检查失败时，本批停止并报警，不写部分结果。

## 11. 验收标准

### 11.1 历史回填

- `112102a..d621afb` 恰有 71 条覆盖记录；
- 十二组缺失事实都能从主题笔记进入对应源材料；
- 旧待办中的 P0、截图识别和 entry_B 状态已经更正；
- `/pro`、测试基线和当前页面结构与项目现状一致；
- 源材料、覆盖表和主题摘要不含密钥与私人交易数据；
- Hermes 整包复核通过，或所有打回项修正后再通过；
- vault 本地与 `origin/main` 一致。

### 11.2 自动同步

- 临时仓库新增一个测试提交后，流水、镜像和摘要都出现该提交；
- 重跑不产生任何 Git diff；
- Hermes 断开时镜像成功、摘要待补，两个游标符合预期；
- 模拟 push 失败时游标不前进；
- 模拟并发启动时只有一个进程写库；
- dirty tree 只报警，不进入正式知识；
- 恢复服务后能从旧游标继续，不漏提交。

## 12. 交付顺序

实施分两个检查点：

**阶段 A：历史回填**

1. 生成 71 提交覆盖清单并完成历史回填；
2. 送 Hermes 整包复核，修正事实冲突；
3. 推送并验证 GitHub 远端。

**阶段 B：持续自动化**

1. 修正现有 vault 同步脚本的拉取、推送和失败判定；
2. 实现同步器、双游标、锁和日志；
3. 接入 Hermes 来源受限摘要；
4. 安装 post-commit hook 与 launchd 兜底；
5. 在临时仓库完成故障注入和幂等测试；
6. 对生产路径做一次 dry-run；
7. 正式启用并验证 GitHub 远端；
8. 把恢复步骤写入 `90-系统/新机器引导.md`。
