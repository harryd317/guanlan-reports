日期：2026-08-08

Prompt：`industry-archive-v2.2-web`

修复提交：`f356e30`

## 1. 结论

生产失败发生在 Kimi 调用之前。档案初稿接口重建 v2.2 数据骨架时，错误地复用了 S8 每日收盘任务的“市场库必须停在温度计快照日”门禁。温度计最近完整快照为 2026-08-04，市场库已推进到 2026-08-07，因此接口抛出 `market_date_mismatch`。本次请求没有发出 HTTP 调用，也没有进入 Kimi API 拒绝或档案规格校验阶段。

生产 LaunchAgent 的配置读取链正常：进程解析出的 `HOME` 正确，默认配置文件存在、可读、权限为 `0600`，解析成功，读到的密钥长度为 51 个字符。验证全程只记录“读到/未读到”和长度，没有输出、写入或镜像同步密钥值及其任何片段。

修复没有改生产 plist，也没有改 Kimi 配置加载方式。S8 每日收盘任务继续执行原有严格日期门禁；只有档案骨架重建可以读取最近完整温度计快照，且行情查询仍以快照日为上限。

## 3. 根因与修复

`load_daily_inputs` 原本同时承担两种用途：

1. S8 每日收盘计算，必须要求温度计快照日等于市场库最新日；
2. 产业档案重建，应该使用最近完整温度计快照，并按该日构造历史骨架。

第二种用途错误继承了第一种用途的最新日门禁。市场库正常前进三天后，旧档案骨架就无法升级到 v2.2。

修复增加显式参数 `require_latest_market`，默认值为 `True`。每日 S8 调用不传参数，行为保持不变。档案重建唯一地传入 `False`；快照日期一致性仍检查，所有市场数据查询仍限定为 `trade_date <= target_date`，不会把快照日之后的行情混入骨架。

错误处理同时补齐以下安全行为：

- 生成抢占前的失败只把安全分类写入 `archive_queue.generation_error`，不改变队列状态；
- 生成抢占后的失败沿用原有回滚，恢复 `skeleton_ready`；
- 日志和队列只保留 `stage=...;code=...`，HTTP 只分 401、403、429、5xx 或其他类别；
- 前端继续显示固定提示，不显示底层异常或响应正文；
- 不做静默降级，通道仍由操作者配置决定。

生产写边界保持不变：与初稿工作流有关的诊断只允许写 `S8_research.db.archive_queue`，不写其他表或生产数据库。
