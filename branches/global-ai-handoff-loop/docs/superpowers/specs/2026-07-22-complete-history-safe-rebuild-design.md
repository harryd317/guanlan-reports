## 1. 结论

系统不丢弃旧会话和旧 Vault，也不再因为原始历史里存在旧凭证而永久禁止上线。迁移改为“原始资料封存 + 全历史脱敏重建 + 干净 Git 基线切换”：

1. 将旧会话、旧 Vault、旧 Git 历史和现有运行状态做成两份本机认证备份。
2. 从 Codex/Claude 原始会话、当前受管 Vault 和可达 Git 历史中重建完整的 AI 可读历史。
3. 只在生成后的暂存内容仍泄露隐私、备份不可恢复、输出不幂等或边界不安全时阻止激活。
4. 以一个无旧父链的干净 Git 根提交替换活跃 `main`；原历史由可验证的实际 Git 元数据快照和 Git bundle 共同保留。
5. 激活后，不同 Codex/Claude 主会话都从同一份项目接力中继续，新反馈再回写原闭环。

本规格替代前置设计第 16 节中“原始 Vault/Git 历史只要命中真实凭证就停止迁移”的规则，也替代交付总结中相同含义的上线前置条件。前置设计的可见主会话边界、S0–S3 分级脱敏、项目隔离、来源链接、八阶段回执和唯一发布器原则继续有效。

## 2. 成功后的使用效果

以“A 股纪律投研台”为例：

1. 用户今天在 Codex 修改项目，系统在背景采集可见主会话。
2. 内容经脱敏、分类和摘要后进入项目日报与“当前接力”。
3. 用户新建 Claude 主会话时，Claude 自动读取该项目的目标、拍板、已完成项、失败尝试和下一步，不要求用户重新解释。
4. Claude 产生的新结论被归档；下一个 Codex 主会话继续该结论。
5. 只有 `collected → sanitized → classified → archived → digested → published → consumed → feedback_archived` 的父子哈希链齐全，状态才显示“已闭环”。

系统继承可安全恢复的旧知识，不局限于炒股。它继续使用六个顶层分类：项目研发、投资财务、个人事务、知识学习、系统运维和综合临时。

## 3. 边界与非目标

### 3.1 本期范围

- 完整盘点本机 Codex 与 Claude 会话源。
- 完整盘点 Vault 中 `20-AI复核/**` 和 `90-系统/AI会话/**`。
- 遍历上述两个受管路径在所有可达 Git 提交中的唯一 blob。
- 对干净 Git 候选根的全部跟踪文件和全部可达对象做发布前安全审计；非受管内容不进入 AI 知识库，但也不能把当前有效凭证重新发布到新根。
- 建立完整的脱敏历史副本、干净 Git 基线、可恢复激活与真实双向接力。

### 3.2 严格不做

- 不修改或删除 Codex、Claude 平台原始会话文件。
- 不让 Hermes 或任何发布任务读取封存备份。
- 不修改实时工作树中受管路径以外的 Vault 正文。干净基线只复制它们在已锁定源提交中的字节；若完整候选树审计发现 S0/S1，激活停止，迁移器不得擅自改写用户正文。
- 不修改炒股工具的交易规则、服务、数据库、定时任务和生产参数。
- 不自动撤销或轮换任何真实凭证。旧凭证风险会明确报告，但不再以“原始资料本来就含凭证”为由永久卡住闭环。
- 本期不采集手机 Codex/Claude/Kimi 应用内的会话。手机端可通过现有 Obsidian/Git 链路查看接力资料；Kimi 适配器后续单独实现。

## 4. 核心安全原则

### 4.1 原始输入是风险源，不是生成结果

迁移器预期原始会话和旧 Git 历史可能含有 S0/S1。原始扫描的作用是建立风险清单、覆盖率账本和轮换建议，不是要求历史在进入脱敏器之前已经干净。

激活门对生成的暂存 Vault、普通运行状态、Hermes 请求、日志、回执、提交元数据以及干净 Git 候选根的完整跟踪树和可达对象图做硬性判定。非受管 Vault 正文按字节保留，不进入 AI 知识库，也不被迁移器改写；但它属于待发布候选树，所以其中的 S0/S1 会阻止远端切换。通过审计且按字节复用的非受管 blob 可以保留原 blob ID，清单必须将它标记为“审计后复用”，不得宣称所有旧 blob ID 都已消失。

### 4.2 原始副本只有恢复权，没有业务读取权

封存备份只能被迁移验证器和回滚器打开。日常采集、分类、摘要、搜索、Hermes 和 Git 发布都不得将备份根目录加入读取范围。

### 4.3 新知识优先，旧知识可追溯

旧日报和旧摘要可能已过时。它们会作为 `legacy-reference` 保留，但不会自动复活为当前硬约束。当前接力按“较新的用户明确拍板 → 较新的主会话 → 当前 Vault 参考 → 旧 Git 历史参考”排序。无法解决的冲突显示为“历史分歧”，不猜测当前规则。

### 4.4 一个持续发布器

`com.harryd317.screener-vault-sync` 继续是唯一持续 Git 发布器。迁移器只能在发布锁内执行一次性、有确认令牌的历史切换；它不能安装第二个持续提交或推送任务。

## 5. 分级脱敏的最终口径

| 级别 | 处理 | 生成副本中的效果 |
|---|---|---|
| S0 凭证 | 完全替换 | 只保留 `[已脱敏：类别]`，不保留头尾字符 |
| S1 身份与账户 | 稳定伪名 | 使用本机 HMAC 生成不可枚举别名 |
| S2 账户级精确资金 | 去精确化 | 总资产、余额、购买力、持仓市值、盈亏金额和精确数量改为区间或比例 |
| S3 决策数据 | 原样保留 | 代码、现价、成本价、买点、止损线、目标价、仓位比例、收益率、回撤率、规则、拍板、失败和复盘不变 |

普通运行状态同样要求 S0/S1 为零。精确本机路径、Git 远端账户和源文件映射只能进入独立的私密路由区：文件权限 `0600`，正文使用 macOS Keychain 持有的独立随机密钥做 AES-256-GCM 加密，解密接口只允许读取预定义字段。Git 配置只保存 `ai-vault::<safe-route-id>`；专用 Git 远端 helper 和 LFS custom transfer agent 在进程内按需解密真实 URL，并从系统凭证存储读取认证信息，真实 URL 和凭证不进入参数、环境变量或普通日志。字段审计拒绝凭证正文、自由文本和未知字段；Vault 内的项目注册表只保留安全项目 ID、显示名、根目录别名和已伪名的远端标识。

脱敏器和独立复检器继续使用两套规则。复检发现生成文本仍含 S0/S1 时，该消息正文不进入 Vault、Hermes、日志或 Git；系统只生成一条无正文的覆盖缺口记录。

## 6. 全历史源盘点

### 6.1 两层统一账本

文件层和记录层使用不同单位，不能用一个文件状态掩盖其中的消息。三类源使用判别联合：

| `source_kind` | 冻结身份 | 记录切分单位 |
|---|---|---|
| `codex_session_file` / `claude_session_file` | 设备号、inode、完整行高水位、前缀 SHA-256 | 每个完整 JSONL 记录 |
| `vault_current` | 设备号、inode、字节长度、全文件 SHA-256 | 默认整文件一条；只有带稳定锚点的适配器才可拆成区块 |
| `vault_git_blob` | blob OID、对象类型、字节长度、全对象 SHA-256 | 默认整 blob 一条；只有带稳定锚点的适配器才可拆成区块 |

文件层公共字段至少记录：

```yaml
ledger_layer: file
source_kind: codex_session_file | claude_session_file | vault_current | vault_git_blob
source_ref: <HMAC 稳定标识>
snapshot_identity: <上表对应的判别联合>
raw_snapshot_sha256: <冻结内容哈希>
file_status: inventoried | snapshotted | parsed | blocked_source | unsupported_source
file_reason: none | source_changed | boundary_violation | special_file | unknown_session_schema | parser_absent
total_records: <整数>
visible_records: <整数>
deferred_append_fragment_bytes: <仅 JSONL 文件使用的非负整数>
terminal_counts:
  imported: <整数>
  duplicate: <整数>
  excluded_by_policy: <整数>
  quarantined_metadata: <整数>
  unsupported: <整数>
  deferred_append: <整数>
```

记录层至少记录：

```yaml
ledger_layer: record
record_ref: <HMAC 稳定标识>
parent_ref: <文件 source_ref>
ordinal: <稳定序号>
raw_sha256: <原始记录哈希>
status: imported | duplicate | excluded_by_policy | quarantined_metadata | unsupported | deferred_append
reason: <闭合集合中的原因码>
sanitized_sha256: <可选>
project_ids: [<项目 ID>]
```

`unsupported_source` 只能使用文件层的 `unknown_session_schema` 或 `parser_absent`；`blocked_source` 只能使用 `source_changed`、`boundary_violation` 或 `special_file`。记录层 `unsupported` 原因码只有 `unknown_session_schema`、`corrupt_record`、`invalid_utf8`、`encrypted_or_compressed`、`oversize_record` 和 `parser_absent`。新增原因必须提升账本版本并补测试，不能写自由文本。非零 `unsupported` 会阻止系统宣称“完整 AI 可读历史”；激活只能在确认令牌同时绑定其逐项安全清单哈希和明确的 `accept_unsupported` 标志后继续。

Vault 文件和 Git blob 默认各形成一条记录；若适配器把它拆成带稳定锚点的区块，文件层必须记录区块总数，并让每个区块取得终态。对会话源，`visible_records` 只统计符合日常接力边界的用户/助手正文；对 Vault/Git 源，它统计可进入 AI 副本的安全可读文件或区块。`total_records` 同时包含按政策排除或不支持的记录。

账本详细版保存在本机普通 `0600` 状态中，只含 HMAC 标识和安全元数据。精确源映射进入加密私密路由区。Vault 只收录按平台、年月、项目、原因码和处理状态汇总的覆盖率，不收录原始路径、命中文本和凭证片段。

### 6.2 会话源

迁移器盘点现存会话源中的全部 `*.jsonl`，不以文件修改时间作为唯一历史边界。活跃短文件、被平台按日期分目录的旧会话和已归档会话都要列入账本。

暂存器只从已打开的文件描述符读取会话：先用 `fstat` 固化设备号和 inode，再确定最后一个完整 JSONL 行的高水位，最后流式读取该前缀并计算哈希。激活备份也从同一个设备号、inode、高水位和前缀哈希定义的不可变视图取数；主、备两份会话副本都从同一份冻结源快照派生，不能分别重读活文件。

激活时允许文件只在认证高水位之后追加。迁移器枚举新增的完整记录并标记 `deferred_append`；不完整尾行只记入文件层 `deferred_append_fragment_bytes`。已暂存前缀被改写、截断或替换时必须重新暂存。新增尾部由激活后的首次增量采集补入，不将正常追加误判为数据丢失。

只有主会话中用户可见的用户/助手文字进入 AI 可读副本。系统提示、隐藏推理、工具输入输出、插件包络、权限包络、附件正文和子代理会话记为 `excluded_by_policy`，不进入日常接力。

### 6.3 当前受管 Vault

当前受管文件按三类处理：

1. 能从原始会话重建的受管原文和摘要，以原始会话为权威源；系统先把现有 Vault 文件与可重建规范版本做结构化差异，规范部分只补充来源证据，不重复复制正文。
2. 无法从 JSONL 重建、但能安全脱敏的旧笔记，导入 `legacy-reference`，保留结构、日期、项目、结论和内部链接。
3. 无法安全产生正文的笔记，只在覆盖率页中显示日期、项目和“存在脱敏缺口”；原文仍可从封存备份恢复。

人工创建但放在两个受管路径内的现有笔记，以及系统生成文件中的人工追加段落，都不会因为缺少 `generated_by` 而被丢弃。能安全分离的人工剩余段落作为 `legacy-reference` 导入；不能可靠分离时，整份旧文件作为历史参考保留，新的规范生成文件使用独立路径。两种情况都标记“非系统原文”并进入文件/记录账本。

可读的 Markdown、YAML 和 JSON 按文本脱敏。二进制文件和无法严格 UTF-8 解码的文件不进入 AI 副本，以 `unsupported` 记入覆盖率账本并留在封存备份。可解析的内部链接通过脱敏映射重写；找不到安全目标的链接显式标记为“历史目标不可用”，不静默指向错误笔记。

### 6.4 受管 Git 历史

系统遍历所有可达 commit 中位于受管路径的唯一 blob。每个 blob 都进入账本。与当前笔记或会话内容重复的 blob 只记来源；其他可安全脱敏的唯一版本进入历史参考库。

历史参考记录保留源提交时间、脱敏后内容哈希和短提交 ID，但不保留可识别账户的原路径。多个提交指向同一脱敏内容时，只保存一份正文和一份时间索引。

### 6.5 覆盖缺口

迁移不得静默跳过任何源对象。最终必须满足：

```text
观测记录总数 = 导入 + 去重 + 按政策排除 + 元数据隔离 + 显式不支持 + 延后追加
```

等式分层计算，不混合单位：会话文件层核对文件数、稳定前缀字节、延后完整记录字节和 `deferred_append_fragment_bytes`，会话记录层核对记录数，Vault 层核对文件及其人工剩余记录，Git 层核对唯一 blob 数和引用数。每个文件的 `terminal_counts` 之和必须等于该文件的观测完整记录数；JSONL 文件还必须满足“激活时观测字节 = 认证稳定前缀字节 + 延后完整记录字节 + 延后片段字节”。总账再按平台、年月和项目复算。

对于可支持的主会话格式，整个文件无法解析或无法建立稳定身份时，暂存失败。单行损坏但其他消息可恢复时，保留文件、行号和日期的安全元数据，并将该行记为覆盖缺口。

## 7. 两份完整封存备份

### 7.1 备份内容

激活产生两份字节独立验证的本机备份，每份包含：

- 本次盘点发现的 Codex/Claude 原始会话文件；
- 完整 Vault 文件系统快照，包括受管与非受管文件、未跟踪文件、原始模式元数据，以及工作树中的 `.git` 文件或目录；
- 通过 `git rev-parse --git-common-dir` 和 `git rev-parse --git-dir` 发现的实际 common gitdir、worktree gitdir、index、config、hooks、logs、objects、refs、packed-refs、shallow、worktrees 和 LFS 对象；
- 由 `git bundle create <bundle> --all` 生成的可移植 refs 封存；bundle 是辅助恢复件，不替代真实 Git 元数据快照；
- AI 同步状态、全局受管指令块、Claude 钩子设置、AI LaunchAgent 和运行副本；
- 恢复顺序、原始文件模式、SHA-256 描述子、源快照指纹和状态机日志。

备份是原始敏感资料的唯一允许扩散例外，用于保护用户珍视的旧会话和旧 Vault。它们必须位于 Vault、源码仓库和所有发布根目录之外。

“字节完整”指快照声明高水位之前的每个字节都一致。对正在追加的会话，迁移器从已认证文件描述符读取到最后一个完整 JSONL 行，把这份不可变源快照先写入认证备份根；第二份备份只能从该快照复制。两份副本完成后再次核对活文件的设备号、inode 和前缀哈希。备份后新追加的尾部属于下一个增量周期，不改变本次备份语义。

Vault 和 Git 元数据也只能读取一次源快照。迁移器先暂停已知写入者并获取仓库锁；在支持时使用同卷只读快照或写时复制克隆，否则执行“复制前源全量清单 → 单次复制 → 主备份全量清单 → 复制后源全量清单”，并要求三份清单逐项相等。这样即使源文件复制期间短暂变化后又恢复，取得瞬态字节的主备份也不能通过。恢复备份只能从认证主快照复制，且其完整清单必须等于主备份清单，不能再次扫描实时 Vault。任何特殊文件、越界符号链接、所有者变化或复制期漂移都会使激活停止。

原始 Git blob 必须通过 `git cat-file --batch` 一类流式接口直接送入脱敏器。不得把原始 blob 写入暂存 Vault、系统临时目录或干净仓库。确需固化的原始字节只能写入认证备份根，并必须进入备份清单和清理验证。

### 7.2 权限与认证

- 备份目录权限固定为 `0700`，文件权限固定为 `0600`。
- 清单记录原始模式，回滚时恢复；备份副本本身不以原始宽权限暴露。
- 主备份和恢复备份各自持有完整正文与签名清单，不共享可变文件。
- 备份清单使用随机生成的 256 位 `migration-recovery-v2` 根密钥。正常运行把根密钥存入 macOS Keychain；离线恢复码是同一根密钥的 `AIMR2-<Base32>-<校验码>` 编码，校验码取 `SHA-256("AIMR2" || 根密钥)` 的前 10 个 Base32 字符。恢复码只显示一次，但可重复用于灾难恢复。每份备份以备份 UUID 为 salt、`ai-migration-backup-manifest-v2` 为 info，通过 HKDF-SHA-256 派生独立 HMAC-SHA-256 密钥。确认令牌只授权本次激活，不能充当长期恢复密钥。
- 备份恢复根密钥与私密路由密钥分别随机生成，不能互换。测试环境使用同一接口的临时密钥提供器，不把测试密钥写入仓库。
- 备份路径、清单和任何原始正文都不进入 Vault、Git、Hermes、通知或普通日志。

备份 AI 运行状态时排除本次和既有 `migration-backups` 子树，避免递归复制。既有迁移备份在本次切换中原地保留，其路径、认证状态和完整性指纹写入新清单。

两份备份都在同一本机磁盘时，它们提供操作回滚冗余，不等同于异地灾备。系统不会将其中一份自动上传到网盘或远端仓库。

### 7.3 激活前恢复演练

每份备份都要独立通过：

1. 清单 HMAC 验证与全文件 SHA-256 复算；
2. Git bundle 完整性检查、认证演练区恢复克隆和 `git fsck --full`；
3. 实际 Git 元数据恢复后逐项核对 HEAD、全部 refs、reflog、index、配置、hooks、LFS、工作树状态和对象集合；
4. 使用清单固定的随机种子，对边界文件和抽样文件做字节对比；
5. 受管目录、全局指令、任务和运行状态的完整恢复演练；
6. 模拟进程重启，只依靠备份、持久恢复凭据和已提交恢复程序完成认证与恢复；另在空 Keychain 环境中只输入离线恢复码，验证版本、校验码、HKDF 派生和清单 HMAC 后完成同一恢复。

任意一份备份或演练失败，激活必须停止。

当前版本继续保留 v1 备份读取与恢复路径。发布 v2 前，仓库必须冻结一份带哈希的 v1 恢复程序或保留兼容实现，并用 v1/v2 固定夹具验证旧备份不会因升级而失去恢复能力。

## 8. 完整历史安全重建

### 8.1 处理流水线

```text
原始源快照
  → 主会话/受管笔记/Git blob 适配
  → S0–S3 脱敏
  → 独立安全复检
  → 内容去重与来源合并
  → 确定性项目分类
  → 原文/历史参考/索引/覆盖率
  → 项目日报与当前接力
  → 生成结果独立审计
```

暂存分类优先使用 Git 根、私有路由注册表、项目别名、平台项目元数据和旧笔记路径。无法确定的安全内容使用 `migration_temporary` 进入“综合临时”和待归类队列。暂存期不为了减少“综合临时”而将原始文本发给在线分类器。

激活后，Hermes 只对已通过复检的待归类内容做限额语义归类。归类只移动索引和项目链接，不复制或改写脱敏原文。

待归类队列不需要用户手工整理。系统按限额自动重试；语义二次归类仍不足 `0.85` 时，自动将其稳定归入“综合临时”。队列最终没有悬空记录。

### 8.2 去重与来源链

脱敏后正规化的消息指纹是去重主键。同一段内容可以有会话、当前 Vault 和多个 Git commit 三类来源，但正文只保存一份。每条日报事实和当前接力事实必须链接到这份脱敏原文或历史参考的消息锚点。

本机账本持有 `source_ref → 封存源` 映射。Vault 内只保留 `source_ref`，不直接链接到敏感备份。

### 8.3 冲突与过时规则

摘要器必须使用时间和来源权威序。一条旧规则只有在较新的主会话或用户拍板明确确认它仍有效时，才能进入“当前硬约束”。

当两条可追溯来源相互冲突且无法确定新旧覆盖关系时，当前接力必须同时列出两条来源并标记“待人工拍板”。它不得选一条冒充当前事实。

### 8.4 确定性清单与激活清单

重建产生两份职责不同的清单：

- `rebuild-manifest` 只含规范化输入指纹、策略版本、账本覆盖率、脱敏输出哈希、状态哈希和候选 Git tree。相同输入重建两次时，它必须字节一致。
- `activation-manifest` 记录生成时间、备份路径、确认令牌哈希、Keychain 密钥标识、远端租约和事务日志。它是一次性事务证据，不参加幂等比较。

重建器不得为了追求字节一致而固定安全随机数。稳定伪名由固定用途密钥和稳定源标识导出；确认令牌、备份 nonce 和事务 ID 每次独立生成，只进入激活清单。

## 10. 干净 Git 历史与远端切换

### 10.1 为什么不在旧历史上追加一个脱敏提交

新提交只能修改当前工作树，旧 S0/S1 blob 仍可从旧 commit 读取。因此，“在旧 `main` 上删除凭证并普通推送”不能构成干净历史。

### 10.2 干净基线

暂存阶段在私有临时仓库中生成一个无父提交的新 `main`：

- 源提交中的所有非受管跟踪文件按字节复制；
- 两个受管路径使用本次脱敏重建结果；
- 未跟踪文件不进入新提交，但保留在实时工作树和两份备份中；
- 提交元数据不包含原始凭证、本机绝对路径和账户身份。

提交前，审计器扫描完整候选 tree、提交元数据和全部可达对象，而不只扫描两个受管路径。非受管文件若命中 S0/S1，迁移器停止并只报告 HMAC 文件标识、规则类型和计数；它不得复制命中片段、自动改写正文或继续强推。只有扫描通过的非受管字节才可进入干净基线。

审计器还必须识别候选 tree 中的全部 Git LFS 指针。每个指针都要解析并核对 LFS OID 和声明大小，再从本地 LFS 存储或远端 LFS 接口把实际正文流式送入同一套独立 S0/S1 扫描器。下载缓存只能位于恢复根密钥认证的审计根内。实际对象缺失、OID/大小不符、无法完整扫描或命中 S0/S1 时，激活停止；`rebuild-manifest` 和 `activation-manifest` 都记录安全 pointer ref、LFS OID、大小、正文哈希和扫描结论，不记录正文或命中片段。

生成干净基线前，源 Vault 必须满足：已跟踪工作树无未提交修改、本地 `main` 与 `origin/main` 一致、远端 refs 已固化。未跟踪文件可以存在，但不能与新基线的跟踪路径冲突。

新仓库的可达对象图中不存在旧 commit、含不安全受管内容的旧 tree、旧的不安全受管 blob 或任何被当前策略判为 S0/S1 的 blob。按字节保留且通过完整候选树审计的非受管文件可以复用 blob ID；全部后代都经审计的纯非受管目录也可以复用 tree ID。清单逐项记录这些“审计后复用”的 blob 和 tree。旧版本的完整可恢复性由双份实际 Git 元数据快照和 bundle 共同保证；其中可用于 AI 接力的历史知识已以脱敏历史参考的形式进入新基线。

### 10.3 远端策略

默认继续使用现有私有 `origin`。暂存器固化安全 route ID、规范化远端 URL 的 keyed HMAC、目标 ref 的 keyed HMAC、旧 OID、候选新 OID 和全部远端 refs 摘要；真实 URL 与完整 ref 名单只存于加密私密路由区。一次性确认令牌必须绑定这些字段。迁移器只能在发布锁内使用等价于 `--force-with-lease=refs/heads/main:<old_oid>` 的条件更新，不能做无条件强推。租约冲突立即停止，不覆盖并发提交。

暂存器必须通过专用 helper 盘点 `git ls-remote` 可见的全部 refs，包括 heads、tags、notes 和自定义 namespace，并把全部可取对象抓入隔离对象库做可达性遍历。该对象库只能位于权限 `0700`、由恢复根密钥认证的审计根内，不能位于系统临时目录或干净仓库；审计后将其纳入备份清单或安全删除并扫描残留。除配置的发布 ref 外，只要另一个可见远端 ref 仍能到达旧受管 blob，激活就停止。系统不会默认删除任何额外 ref。代码托管商不公开、客户端无法枚举的内部保留引用只能列为托管商残留风险，不能冒充已清除。

更新后必须重新计算远端 URL keyed HMAC，并读取目标 OID 和 refs 摘要。远端 ref 更新不保证代码托管商立即物理清除不可达对象。因此，若风险清单显示真实且仍有效的凭证曾进入远端，轮换仍是安全建议。未轮换会显示为未解决风险，不冒充“凭证已安全”。

### 10.4 电脑与手机客户端

远端历史切换后，仍持有旧父链的其他 Git/Obsidian 客户端不能直接普通拉取合并。系统维护一个显式客户端注册表，为每台电脑、手机和发布节点保存安全客户端 ID、期望 ref 和最近回执。每个已注册客户端都要执行“本地备份 → 重新克隆或受控重置 → 校验 `origin/main` 哈希 → 写入客户端回执”。在全部已注册客户端完成前，状态必须显示“远端已切换，客户端待重连”；未注册设备不计入完成度，报告也不得笼统声称“所有手机和电脑已同步”。

## 11. 新迁移门模型

### 11.1 `plan`：输入盘点门

`migrate plan --all-history` 只读并输出三类结果：

```yaml
gate_version: 2
inventory_complete: true
staging_allowed: true
input_risk:
  credential_findings: <数量>
  identity_findings: <数量>
  rotation_recommended: true | false
activation:
  ready: false
  reason: not_staged
```

`gate_version: 2` 使用 `staging_allowed` 和分阶段 `activation.ready` 替代含义混杂的旧 `safe_to_activate`。`plan` 退出码只表示能否安全进入暂存，不表示已获准强推或激活。

生产激活清单只能由 `--all-history` 产生。`--since <date>` 可继续用于只读影子预览和性能调试，但不得生成可激活清单。

原始 S0/S1 命中不将 `staging_allowed` 改为 `false`。以下情形才阻止暂存：输入边界越界，临界路径是符号链接，源文件在读取期间改变，Git 对象损坏，受支持的主会话整体不可解析，或无法生成完整覆盖率等式。

### 11.2 `stage`：生成结果门

`migrate stage --all-history --staging-vault <私有绝对路径>` 先固化一份输入高水位清单，再对同一组文件描述符、完整行边界和 Git 对象 ID 执行两次重建。第一次可生成摘要；未变输入的第二次必须零 Hermes 调用、零受管文件差异、零状态差异、零新回执，且两份 `rebuild-manifest` 字节相同。包含时间、随机 nonce、路径和确认令牌的 `activation-manifest` 不参加幂等比较。

暂存硬门全部通过后才生成认证激活清单和一次性确认令牌。清单固化源快照指纹、全部候选跟踪文件哈希、普通状态哈希、加密私密路由区哈希、干净 Git 根、安全 route ID、规范化远端 URL/目标 ref 的 keyed HMAC、旧/新 OID、远端 refs 摘要、覆盖率等式、逐项不支持清单、隔离数、脱敏计数和策略版本。

### 11.3 激活硬门

以下任一条成立时，`activate` 必须拒绝：

1. 生成的受管 Vault、普通运行状态、Hermes 提示、回执、日志、完整 Git 候选 tree/可达对象、候选 tree 引用的实际 LFS 正文或提交元数据存在 S0/S1；私密路由区出现未知字段、凭证或未加密正文；
2. 任一结构化 S2 字段仍保留账户级精确值，或任一结构化 S3 字段在前后证明中发生语义修改；
3. 源快照、暂存清单、清单认证、策略版本、安全 route ID、远端 URL/目标 ref keyed HMAC、旧 OID 或远端 refs 摘要与暂存时不一致；正常活跃会话只允许在已认证高水位后追加；
4. 两次重建不幂等，或未变第二次仍发生 Hermes/文件/回执变化；
5. 任何输入、暂存、备份、运行或发布路径越界，或存在符号链接、特殊文件、不可信所有者；
6. 覆盖率等式不成立，存在静默丢失，支持格式整体不可解析，或存在未由确认令牌绑定并明确接受的 `unsupported` 项；
7. 两份封存备份未完成，未通过进程重启后的恢复演练，实际 Git 元数据不能完整还原，或事务回滚不能恢复迁移器修改的本地对象与原远端父链；
8. 新 Git `main` 不是无父干净根，存在可达旧 commit、含不安全受管内容的旧 tree、策略禁止的 blob，或非受管跟踪文件与锁定源提交不同；清单中的已审计纯非受管 tree/blob 复用除外；
9. 唯一发布锁无法获取，远端租约无法建立，更新无法校验，或额外远端 ref 仍指向旧受管历史；
10. 固定阶段枚举中的失败注入演练不能进入规定的已恢复、待远端恢复或本地冲突状态。

原始会话和旧 Git 历史中的凭证命中、元数据隔离计数非零、存在综合临时队列，不是激活硬阻断。当前非受管候选文件中的 S0/S1 属于将被重新发布的生成结果，必须阻断。所有非阻断风险都要显示在风险和覆盖率报告中。

## 12. 激活事务

### 12.1 在线激活与事务回滚

激活使用固定顺序：

1. 验证暂存清单和一次性确认令牌。
2. 获取唯一发布锁，暂停旧 AI 任务与 Vault 发布任务。
3. 复核源快照、活跃会话高水位、跟踪与未跟踪工作树、实际 common/worktree gitdir、index、HEAD、全部 refs、reflog、对象集合、安全 route ID、远端 URL/目标 ref keyed HMAC 和远端 refs 摘要；除认证高水位后的会话追加外，任何漂移都要求重新暂存。
4. 从每个已打开源的冻结视图和同一份 Vault/Git 快照创建主备份，再只从主备份内容派生第二份恢复备份；分别认证并验证。
5. 在每份备份根内权限 `0700` 的认证恢复演练区完成恢复；演练区进入清单，演练后做安全清理和残留扫描，不能使用系统临时目录。
6. 在任何实时修改前再次复算第 3 步全部指纹。备份或演练期间出现用户编辑、Obsidian 写入、Git 提交、index/refs/对象变化时安全中止，不改本地或远端。指纹稳定后，用认证暂存状态替换旧 AI 运行状态，用脱敏受管目录替换旧受管目录。
7. 用干净 Git 根替换本地活跃仓库元数据，验证工作树、未跟踪文件和新 `main` 完全对齐；原 common gitdir 和 worktree gitdir 只能在两份恢复演练通过后切换。
8. 使用绑定旧 OID 的 `--force-with-lease` 更新 `origin/main`，再从远端读回对象哈希、refs 摘要与完整候选树清单。
9. 安装已提交的运行副本、全局受管指令块和任务定义，但保持 AI 采集任务与发布器禁用。
10. 运行只读本地冒烟、远端发布校验、项目接力读取和状态一致性检查。
11. 将备份状态从 `prepared` 推进到 `activated`，提交事务完成状态。
12. 启动 AI 采集任务；健康检查通过后最后恢复唯一发布器。首次采集使用新的增量 epoch，不参加激活快照验证。启动失败进入 `activated_service_degraded`，保持发布器停用，不回滚已验证的历史切换。

事务回滚只恢复本次迁移器实际修改的对象。替换前后都保存受管目录、状态、指令、任务和 Git 元数据指纹；失败时，只有当前对象仍等于迁移器安装版本，回滚器才可恢复旧版本。若对象既不等于旧版本也不等于安装版本，回滚器先把并发修改保存到认证冲突区，再进入 `rollback_local_conflict`，不得覆盖用户新内容或报告“已恢复”。非受管 Vault 正文从未被事务修改，因此事务回滚不得用整库备份覆盖它。

远端回滚只能使用 `--force-with-lease=refs/heads/main:<clean_root_oid>` 恢复原 OID。租约冲突进入 `rollback_remote_pending/conflict`；网络不可用进入 `rollback_remote_pending/network`。两种状态都保留已认证旧/新引用，禁止重启发布器，绝不做无条件强推。

### 12.2 灾难恢复

灾难恢复与事务回滚是两条命令和两套权限。灾难恢复在用户明确选择备份后执行，先停止全部写入者，再给当前现场做第三份安全快照，最后才可恢复完整 Vault、实际 Git 元数据、运行状态和任务。它必须验证 HEAD、全部 refs、reflog、index、配置、hooks、LFS、对象集合和工作树状态，不能只恢复 bundle。

v1 备份由冻结的 v1 恢复器处理，v2 备份由本规格的恢复器处理。恢复器拒绝未知版本，不自动升级备份清单。

### 12.3 固定事务阶段与失败状态

状态机只使用以下阶段：`validated`、`locked`、`snapshotted`、`restore_tested`、`local_switched`、`remote_switched`、`installed_disabled`、`smoked`、`committed` 和 `services_started`。失败注入逐阶段覆盖，并只允许下列结果：

| 失败位置 | 允许结果 |
|---|---|
| `local_switched` 之前 | `aborted_no_live_change` |
| `local_switched` 至 `remote_switched` 之前 | `rolled_back_local` 或 `rollback_local_conflict` |
| `remote_switched` 至 `committed` 之前 | `rolled_back`、`rollback_local_conflict`、`rollback_remote_pending/conflict` 或 `rollback_remote_pending/network` |
| `committed` 之后 | `activated_service_degraded`；不重写已提交历史 |

## 13. 激活后的时效与降级

- 可见主会话原文通常在 5 分钟内归档。
- 项目内容静稳 3 分钟后进入摘要，常见端到端延迟为 5–15 分钟。
- 新主会话启动时发现落后，最长等待 300 秒补齐；超时后读取上一份有效接力并标记“最新内容尚未归纳”。
- Hermes 或网络失败时，脱敏原文和待归类队列仍保留；摘要不更新，状态不伪造成功。
- 不同项目不共享详细原文。无法判定项目的内容继续留在“综合临时”，不混入炒股工具或其他既有项目。

## 14. 测试与验收

### 14.1 覆盖率

1. 所有现存、格式受支持的 Codex/Claude 源文件都进入迁移账本。
2. 所有合格主会话可见消息要么生成脱敏原文，要么生成无正文的明确缺口；不存在静默丢失。
3. 当前受管 Vault 文件和所有可达受管 Git blob 全部进入账本。
4. 文件层、记录层和延后追加等式对每个平台、源类型、年月和项目均成立；每个 `unsupported` 都有闭集原因码和显式处置。
5. 每个现有受管 Vault 文件都与规范重建结果做差异；人工追加内容要么进入 `legacy-reference`，要么成为显式缺口。

### 14.2 隐私与语义

1. 生成的受管 Vault、普通状态、提示、日志、回执、完整 Git 候选 tree/可达对象和提交元数据中 S0/S1 命中为零；私密路由区只含允许字段和认证密文。
2. 每条结构化记录的全部 S2 字段都有前后证明，精确值不可由同文分母逆推；不得只验证固定样本。
3. 每条结构化记录的全部 S3 字段都有前后逐字段证明：数字按类型规范化，字符串按换行和 Unicode 规范化后逐字节相等。无法结构化的自然语言结论进入固定种子抽样和人工语义验收，不由程序伪称“语义相等”。证明清单只保存字段类型、策略结果和前后 HMAC；S2 原始精确值不进入普通状态或日志。
4. 对非结构化内容使用清单固定的随机种子，按明确的 `collected`、`sanitized`、`classified`、`archived`、`digested`、`published`、`consumed` 和 `feedback_archived` 阶段分层抽样；旧规则不得被错误复活。
5. Hermes 出口拦截器只记录请求哈希、策略版本和扫描结果，不记录提示正文或命中片段。
6. Git/LFS 配置、进程参数、环境变量和普通日志中只出现安全 route ID；真实远端 URL 和认证信息只在 Git helper 或 LFS custom transfer agent 的受限解密路径中出现。

### 14.3 幂等、备份和 Git

1. 两次重建的受管文件、普通状态、`rebuild-manifest` 和覆盖率结果字节一致；未变第二次零 Hermes 调用。随机的 `activation-manifest` 单独验证，不参与比较。
2. 两份备份均通过清单、进程重启、恢复克隆、`git fsck --full` 和实际 Git 元数据完整恢复；恢复后 HEAD、refs、reflog、index、配置、hooks、LFS、对象集合和工作树状态一致。
3. 新 `main` 只有一个无父根提交；可达对象图不含旧 commit、含不安全受管内容的旧 tree 或策略禁止的 blob，已审计纯非受管 tree/blob 复用均在清单中；本地与远端提交哈希一致。
4. 远端并发提交使前向租约失败且不覆盖对方提交；回滚租约冲突进入 `rollback_remote_pending/conflict`，绝不无条件强推。
5. 固定阶段枚举中的每个事务阶段都有失败注入测试；本地并发编辑进入认证冲突区，远端中断进入真实待恢复状态。
6. v1/v2 固定备份夹具均能由对应恢复器验证和恢复；未知版本被拒绝。
7. 原始 Git blob 全程流式处理；暂存 Vault、系统临时目录和干净仓库中不存在未列入认证备份的原始 blob 副本。
8. 在备份复制和恢复演练期间分别注入 Vault 编辑、index 变化、本地提交、ref 更新和新对象；系统必须在任何实时切换前检测并以 `aborted_no_live_change` 停止。
9. 在空 Keychain、全新进程环境中，只凭 v2 备份和离线恢复码完成 HMAC 认证与完整恢复；错误版本、错误校验码和错误密钥均被拒绝。
10. 在普通复制回退路径中注入“复制期间修改、复制后恢复原字节”，系统必须因主备份清单不等于复制前后源清单而停止；恢复备份清单还必须逐项等于主备份清单。
11. 候选树中的 LFS 指针、实际对象 OID、声明大小和正文哈希逐项一致；缺失对象、伪造大小、正文 S0/S1 命中和不可完整扫描都阻止激活，扫描过程不在认证审计根外留下正文。

## 15. 交付边界

“代码完成”、“暂存通过”、“本地激活”、“远端切换”、“客户端重连”和“真实双向接力通过”是六个不同的交付状态。只有最后一个状态完成，才可以对用户说“跨软件闭环已经可用”。

若电脑端 Codex/Claude 已闭环，但手机 Vault 还未重连，结论必须写为“电脑端闭环可用，手机笔记同步待恢复”。若 Kimi 适配器未实现，结论必须写为“Codex/Claude 已接入，Kimi 未接入”。
