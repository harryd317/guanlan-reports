# 产业温度计生产端收尾设计

**日期：** 2026-08-02
**状态：** 用户批准方案与生产 sidecar 空间
**范围：** 温度计生产数据源、收盘后快照发布、陈旧日期提示、档案首个 H1 去重

## 1. 现场事实

生产 `/api/industry-thermometer` 当前返回 `T1 数据未就绪`。生产 `S3_research.db` 只有表结构和 7 条失败审计记录；`cluster_daily`、`daily_vol` 都是空表。完整冻结 T1 快照位于保留的 T1 工作树，大小为 1,767,968,768 字节，数据截至 2025-12-31，验收 SHA-256 为：

`111f2017d476e87dfdc68d3541d7678630d466d410a91f4ab37d8bcb9ce049d5`

生产 `market.db` 的最新交易日为 2026-07-31。冻结 T1 快照不能直接满足每日更新。

## 2. 方案比较与选择

### 方案 A：生产专用 live sidecar + 快照表（采用）

从冻结 T1 快照创建独立的新库。新库先回填 2026-01-01 至最新交易日，此后复用现有 S3 收盘增量计算。增量发布成功后，系统在 sidecar 内原子写入一行温度计快照。页面只读快照表。

该方案把重计算移出 HTTP 请求，保留 T1 原口径，并让失败日继续展示上一份成功快照。

### 方案 B：生产只读挂载 live T1，请求时计算

该方案改动较少，但每天数据库换日后的首个请求承担全量计算。计算超时会直接影响页面，且没有独立的“全部成功才发布”边界。

### 方案 C：收盘后生成 JSON 文件

该方案读取快，但新增非 SQLite 状态文件与原子替换规则。既有 T1 审计、日期唯一性和事务能力无法复用。

## 3. 不可变边界

1. 冻结 T1 快照永远以 SQLite 只读方式打开。任务不得写入、移动、覆盖或重命名它。
2. 回填前后都计算冻结快照 SHA-256。两个结果必须等于既有验收值 `111f2017…49d5`。
3. 新写路径只允许生产专用 sidecar 及其 `industry_thermometer_snapshots` 表。现有 `S3_research.db`、`market.db`、`screener.db` 不得因本任务产生写入。
4. 回填区间固定为 2026-01-01 至生产行情库的最新交易日；当前目标日为 2026-07-31。
5. 回填与日增量只使用 T1 已批准的数据接口和字段。额度不足、接口失败或字段缺失时立即停止并报告，不调用替代数据源，不猜测字段，不缩减口径。
6. 不修改策略、风控、选股、交易、记账或通知语义。温度计继续是只读展示。

## 4. sidecar 生命周期

生产 sidecar 使用新文件 `industry_thermometer_sidecar.db`。创建流程如下：

1. 验证目标文件不存在，避免覆盖旧文件。
2. 记录冻结 T1 快照 SHA-256。
3. 复制冻结快照到临时 sidecar 路径；复制后校验逻辑完整性和初始哈希。
4. 只在临时 sidecar 上执行 2026-01-01 至最新交易日回填。
5. 验证目标日期、必需表、数据覆盖、`PRAGMA quick_check` 和温度计四灯完整性。
6. 生成首份温度计快照。
7. 再次验证冻结 T1 快照 SHA-256。
8. 关闭所有连接后，把临时 sidecar 原子改名为生产文件。

任何检查失败都保留冻结快照和现行生产配置，不安装 sidecar。

## 5. 收盘任务顺序与发布门禁

现有 S3 hook 改为调用一个失败隔离的生产流水线。流水线的逻辑顺序固定为：

1. **S3 增量计算：** 使用既有 T1 接口获取当天输入并计算 breadth、cluster 和成员结果。此阶段不发布快照。
2. **sidecar 增量发布：** 复用既有 runner 的校验与事务，把当天原始和派生结果提交到生产 sidecar。只有 `published=true` 才进入下一阶段。
3. **温度计快照发布：** 从已提交的 sidecar 和只读 `market.db` 计算四灯。系统验证 `data_date` 等于任务交易日后，在独立事务中写入 `industry_thermometer_snapshots`。

三个阶段都成功，当天快照才更新。S3 计算失败、sidecar 事务回滚、日期不一致或快照写入失败时，流水线只记错误；已有快照保持不变。原 EOD 主任务仍不等待该后台任务，也不因温度计失败而失败。

每次流水线记录三个阶段的状态、目标交易日、已发布快照日期和错误类别。日志不得包含接口凭据或原始大批量数据。

## 6. 快照表与只读 API

快照表位于 sidecar：

```sql
CREATE TABLE industry_thermometer_snapshots (
    trade_date TEXT PRIMARY KEY,
    formula_version TEXT NOT NULL,
    payload_json TEXT NOT NULL,
    generated_at TEXT NOT NULL,
    source_sidecar_sha256 TEXT NOT NULL
)
```

写入使用显式事务和 `INSERT ... ON CONFLICT(trade_date) DO UPDATE`。`payload_json` 保存现有温度计 API 的公开聚合结构，不保存账户、交易或接口凭据。

`GET /api/industry-thermometer` 不再请求时扫描原始 T1 表。它用 SQLite URI `mode=ro` 和 `PRAGMA query_only=ON` 读取最新快照，再只读查询 `market.db` 最新交易日。响应增加：

- `data_date`：快照交易日；
- `latest_trade_date`：生产行情库最新交易日；
- `is_stale`：两者不相等；
- `generated_at`：快照生成时间。

快照表不存在或为空时，API 保留诚实空态。读取失败不得回退到其他数据源。

## 7. 页面日期文案

前端使用 API 明确字段，不用浏览器日期猜交易日：

- 快照为最新交易日：`数据截至M月D日`；
- 快照不是最新交易日：`数据为M月D日`；
- 无快照：`数据未就绪`。

陈旧快照仍显示四档药丸，但日期文案必须可见。前端不隐藏旧数据，也不把旧数据写成“今日”。

## 8. 档案首个 H1 去重

档案元数据继续使用正文第一个 Markdown H1 作为阅读区标题。渲染正文时只移除第一个 `# 标题` 行及紧随的一行空白；后续 H1、H2、表格和正文保持不变。没有 H1 的档案继续使用文件名作为标题，正文不删行。

后端仍禁用 Markdown 原始 HTML，前端继续只插入后端已过滤的 HTML。

## 9. 生产配置

LaunchAgent 增加以下环境变量：

- `S3_RESEARCH_DB=<生产 sidecar 绝对路径>`：现有 S3 hook 与只读 S3 视图使用；
- `T1_RESEARCH_DB_PATH=<同一 sidecar 绝对路径>`：温度计计算与个股行业匹配使用；
- `S3_MARKET_DB=<生产 market.db 绝对路径>`：增量任务明确行情库；
- `INDUSTRY_THERMOMETER_DB_PATH=<同一 sidecar 绝对路径>`：快照读写入口。

配置切换前保存 plist 和三份现有生产数据库哈希。配置切换后执行标准 `restart.sh`；随后核对健康指纹、API 日期、四档药丸和旧生产数据库哈希。sidecar 作为本任务唯一新增可变数据库单独记录安装前后哈希。

## 10. 测试与验收

测试必须先失败再实现，覆盖：

1. sidecar 与冻结快照路径不同；冻结快照用只读连接，哈希前后不变。
2. 回填起止日严格为 2026-01-01 和最新交易日。
3. 批准接口失败、额度不足、字段缺失时停止；没有替代接口调用。
4. S3 计算、sidecar 发布、快照发布三阶段顺序固定。
5. 任一阶段失败时最新快照日期不变。
6. 快照写入原子、同日幂等、跨日只追加。
7. API 只读快照；最新和陈旧日期字段正确。
8. 前端显示四档颜色药丸、数据日期和精确陈旧文案 `数据为X月X日`。
9. 档案阅读区不重复第一个 H1，后续标题和表格保留。
10. 新聚焦测试、项目规定四组回归、JavaScript 语法和 `git diff --check` 全部通过。

生产等效验收使用 sidecar 的只读副本。生产验收截图至少包含桌面和手机温度计总览，画面同时显示冷、温、热、烫药丸和数据日期。生产重启后重复同一检查。
